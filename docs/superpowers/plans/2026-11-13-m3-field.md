# M3 Field and Verification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Once a responder accepts, record what happens in the field and how far it can be believed:
- the responder's "My incident" menu, with T5, T6 and T7 set by the database;
- the cannot-find and unsafe-withdrawal flows;
- caller confirmation by call, by a return USSD session, and by polling when a responder goes silent (this replaces M2's interim follow-up);
- plausibility bounds, the variance monitor, arrival grades and evidence flags;
- the Tool 2 form with the outbreak escalation;
- handover-slip corroboration and weekly reconciliation.

This proves scenario 12 and completes scenario 1 up to payment.

**Architecture:**
- **Field statuses.** Field statuses are incident events written by one SECURITY DEFINER function, `op.report_field_status`. It keeps a row in `op.field_events` and the event in step, as M2's dispatch functions do. `op.append_event_core` refuses a field event whose payload does not name that function's own, still-unlinked row. This closes the generic append to field events without touching `op.append_incident_event`.
- **Verification records.** Verification results, Tool 2 reports and handover slips are records, not state changes. Each goes into its own table through its own function. Each also writes a ledger entry carrying only IDs and a salted hash, the pattern of `op.log_control` in 0016. A closed incident never needs a new event, so weekly slip reconciliation works after closure.
- **Planning.** Verification planning is a pure planner, `field.Plan(state, params, now) → (actions, nextWake)`. The dispatch engine runs it in the same pass, once the dispatch planner has settled, on the same timer row per incident (ADR-0024).
- **Where the calls happen.** ivr-controller places the caller-confirmation calls. intake-gw serves the responder menu and the caller's return session.

**Tech Stack:**
- Go 1.27.4 and PostgreSQL 18.6.
- The in-house ARI client and `sim.FakeARI`, and the Africa's Talking USSD adapter.
- The pinned sqlc v1.31.1 binary.
- No new dependency.

## Global Constraints

**The 14 hard constraints (Build Prompt §3), as they bind M3:**
1. **Data in Uganda.** No new outbound host and no new egress allowlist entry. Confirmation calls use the existing Asterisk trunk.
2. **Basic phone first.**
   - Every responder step is on the USSD responder code.
   - The caller confirms on the keypad of a voice call or in a USSD session.
   - Nothing needs data, an app or a smartphone.
3. **Deterministic; no model lowers severity.**
   - Plausibility, variance and grades are pure functions of recorded facts and of a versioned parameter set (`config/gated/field.yaml`), stamped as `<field version>+sha256:<12 hex of the gated config>`.
   - Tool 2's scene severity is stored beside the incident's severity and never written to it.
4. **Server-side time.**
   - T5, T6 and T7 are `clock_timestamp()` inside `op.append_event_core`, at the moment `op.report_field_status` writes the status: the server receives the report and the database dates it (§10.6). They are first-wins.
   - No handset time and no time typed by a responder is ever a T-time. Tool 2 never asks for an arrival time.
   - The tourniquet time is a clinical note for the receiving unit, stored as `HH:MM` text, never as a `timestamptz`.
5. **Never reveal the caller's number.**
   - The confirmation call opens `op.caller_contact` only to dial it, shows Sauti's number (`SAUTI_ARI_CALLER_ID`) and never logs it.
   - The return session recognises the caller by the keyed hash only.
   - No responder-facing screen gains caller data.
6. **No patient data on messaging apps.** M3 adds no SMS template and no messaging integration. Tool 2 codes travel only in the responder's own USSD session.
7. **No coordinator override.**
   - M3 gives coordinators no dispatch action.
   - After an unsafe withdrawal the role stays held, and the coordinator is rung.
   - Entering and reconciling slips is data entry under a staff ID.
8. **Audit carries only incident and staff IDs.** Every new ledger entry is: type, incident ID (or none), staff ID (or none), logic version, and the salted SHA-256 of a payload built from typed columns.
9. **Five separate stores.**
   - Every new table is in the operational store, in migrations `db/operational/migrations/0029`–`0032`.
   - Nothing changes in the analytic, linkage, audit or media schemas.
   - Grades and flags reach the analytic store only through M6.
10. **Consent gates the export.** M3 exports nothing.
11. **Amendment gate.** `config/gated/tool2.yaml` (the Tool 2 list, named in rule 11) and `config/gated/field.yaml` are gated and count toward the fingerprint.
12. **No new record kind without the DPO.**
    - The authority for `field_events`, `verifications`, `responder_reports` and `handover_slips` is Build Prompt §9 ("Field and verification").
    - `op.confirmation_calls` holds the attempts of the caller-confirmation verification, as `op.alert_attempts` holds alerts' attempts.
    - `op.return_session_pins` is session state pruned after one hour, like `op.responder_menu_pins`.
    - **Not stored:** the Guide §10 optional scene code, any Tool 3 clinical field, any free text.
13. **No access from outside Uganda.** M3 adds no endpoint. The new `sautictl` subcommands run on Sauti's servers.
14. **Dispatch first, fail safe to a human.**
    - The field planner runs only after the dispatch planner returns no action in that pass.
    - Each of these rings the coordinator through the existing `incident.escalated` → `op.claim_coordinator_calls` path:
      - cannot-find;
      - unsafe withdrawal;
      - a caller's "no";
      - an unanswered silent-responder poll;
      - an outbreak report.
    - Verification never delays an alert.

**Interaction standards (ADR-0029).** The "My incident" menu, the cannot-find and withdrawal screens, the Tool 2 form, the caller's return session and the caller confirmation call follow ADR-0029:
- **Keys.** Options 1–9 in order with no gaps, and a recurring choice keeps its digit. On USSD, `0` goes back one screen and `*` is never a key. On the confirmation call, `*` repeats and `#` ends number entry.
- **Retries.** On USSD, a re-prompt names the problem for that input. The confirmation call replays after 10 s of silence at most twice, then hangs up, and an answered call with no key counts as unanswered.
- **A person at the end.** Every failure or exhausted retry records an `incident.escalated` event that rings the coordinator, and never in the same step as a closure.
- **Language.** The incident's Tool 1 language is used for the return session and the confirmation call.
- **Trust.** The confirmation call presents `SAUTI_ARI_CALLER_ID`.
- **Shared flags.** M3 shares the reason registry and the escalation tiers that the UX-hardening plan (`docs/superpowers/plans/2026-11-13-ux-hardening.md`) adds. A new reason has a recording and a runbook row before it is emitted.

## Review Focus

1. **A field status that is duplicated, retried or out of order.**
   - Cases: a USSD callback retried after its status committed; "Leaving with the patient" before "Arrived"; "Arrived" after an unsafe withdrawal; a second responder arriving after the patient left; a status after closure.
   - Expected: one record per responder and status; the retry gets the identical screen; an out-of-order report is refused with a screen that names what to report first; T5, T6 and T7 never move.
   - Tests: Task 2 `TestReportFieldStatusIsOncePerResponderAndStatus`, `TestReportFieldStatusOrder` and `TestSecondResponderArrivalKeepsT5`; Task 3 `TestARetriedStatusGetsTheSameScreen`.
2. **A responder who goes silent, and a confirmation call nobody can answer.**
   - Cases: no status after acceptance, while the caller does not pick up, has no reachable number, or ivr-controller is down.
   - Expected: the coordinator is rung by `silent_after + answer_timeout` at the latest, whether or not any call was placed; a later "yes" stops polling; closure stops everything.
   - Tests: Task 6 `TestSilentResponderIsPolledThenEscalated` and `TestAnUnansweredPollEscalatesEvenWhenNoCallWasPlaced`; Task 8 `TestSilentResponderPollsTheCallerThenEscalates`; Task 9 `TestConfirmCallWithoutAContactFails`.
3. **A returning caller with a new emergency.**
   - Cases: a caller whose incident awaits confirmation dials the caller code about a different emergency, presses a key the question does not offer, or the callback is retried.
   - Expected: the first screen offers the new emergency; "0" reaches Tool 1's first screen with nothing lost; the question appears at most once per session and never outside the window.
   - Tests: Task 7 `TestReturnSessionIncidentIsPinnedAndWindowed`; Task 10 `TestReturningCallerWithANewEmergencyReachesTool1` and `TestReturnSessionIsPinned`.
4. **Plausibility edges.**
   - Cases: an arrival exactly at the bound; the same zone seconds after acceptance; a ward-level incident; a responder whose stage is not in the gazetteer in force.
   - Expected: an arrival exactly at the bound is plausible; distance 0 is never flagged; a ward-level incident uses the nearest zone of its ward; a responder with no place gets no plausibility record (never a false flag); no flag ever changes T5.
   - Tests: Task 5 `TestImplausibleBounds`; Task 6 `TestUnplacedResponderGetsNoPlausibility`; Task 7 `TestVerificationNeverMovesTimestamps`; Task 8 `TestPlausibilityUsesTheNearestWardZone`.
5. **A Tool 2 form submitted twice, after closure, or with the outbreak option on a retry.**
   - Expected: the first report stands unchanged; a retried final callback gets the same "saved" screen; another session's report is refused as already submitted; after closure nothing is written and the screen says so; the outbreak escalation rings the coordinator once.
   - Tests: Task 14 `TestSubmitResponderReportOnceAndFirstWins`, `TestReportAfterClosureIsRefused` and `TestOutbreakReportEscalatesOnce`; Task 15 `TestARetriedFormSubmitGetsTheSameScreen`.

## Open decisions (safe default, flagged)

Each decision becomes a row of the spec §3 register and is recorded in the part's ADR.

| # | Question | Safe default (M3) | Owner | Where |
|---|---|---|---|---|
| O12 | How often is the caller asked when a responder goes silent (Build Prompt §10.4 does not set the interval)? | Silent means no field status from any responder since the first acceptance. The caller is asked at `silent_after` (20 m, M2's interim value) and then every `caller_poll_interval` (10 m) until `caller_poll_until` (30 m after acceptance, Guide §10). The first poll without a "yes" within `answer_timeout` (2 m) escalates `assigned_follow_up` once. | PI | `field.yaml` |
| O13 | How long, and how often, is an arrival confirmed with the caller? | A call at the first arrival, retried every `arrival_call_retry` (5 m) while unanswered until T1 + `confirmation_window` (60 m). Then `caller_unreached` is recorded. A "no" rings the coordinator (`arrival_denied`). | PI | `field.yaml` |
| O14 | What are the plausibility bounds? | A lower bound only. An arrival is implausible when the time since that responder's acceptance is under `min_per_zone` (60 s) × the Chebyshev distance between their stage zone and the incident zone (the nearest ward zone for a ward-level incident). | PI | `field.yaml` |
| O15 | When are a responder's intervals too regular to be credible (§10.7 item 4)? | Over the responder's last `window` (10) acceptance-to-arrival intervals, with at least `min_intervals` (5), a coefficient of variation below `max_cv` (0.10). | PI | `field.yaml` |
| O16 | How are arrivals graded? | `corroborated` (a positive flag and no negative), `attested` (neither), `conflicting` (any negative), `none` (no arrival). Grades block nothing in M3; payment holds by grade are M4's question, with O5. | PI | ADR-0031 |
| O17 | After an unsafe withdrawal, is the role re-alerted? | No. The assignment stays open, so the planner never re-alerts the role, and the coordinator is rung (`scene_unsafe`). A re-dispatch is an M5 coordinator exception, logged as a deviation (rule 7). | Medical Director | ADR-0030 |
| O18 | Is Tool 2 accepted after closure? | No. The form is offered only while the incident is open; a submission racing a closure hears "closed" and nothing is written. M5's close must warn when a report is missing. | PI | ADR-0032 |

**Not built in M3 (flagged in the ADRs):**
- the Guide §10 two-digit scene code (a new data item: DPO and PI);
- field status by voice (§10.6 names USSD; the `ReportFieldStatus` command already carries the channel);
- caller confirmation by an inbound call to the IVR line (§10.7 names a return *USSD* session);
- Guide §8 pattern checks on repeated caller–responder pairs and call rates per number (not one of §10.7's four checks; M5/M6).

**How M3 relates to M2's interim follow-up (ADR-0028).**
- **What M2 built:** `dispatch.Plan` escalates `assigned_follow_up` once when an incident is still open `follow_up_after` (20 m) after its first acceptance. That deferred §10.4's caller question to M3, because silence needs field status and an answer needs a verification record.
- **What Part B (Task 8) changes:**
  - It deletes that rule, `Params.FollowUpAfter`, `config.Dispatch.FollowUpAfter`, `dispatch.yaml: follow_up_after` and `dispatch.ReasonFollowUp`.
  - The field planner keeps the reason code `assigned_follow_up` (its IVR prompt and every stored escalation stay valid), as `field.ReasonSilent`, and moves the 20 m to `field.yaml: silent_after`.
- **Effect:** a silent incident now asks the caller first, and escalates no later than 20 m + 2 m whether or not the call happens. An incident with any field status is no longer escalated merely for being open, and arrivals go through confirmation instead.
- ADR-0031 supersedes ADR-0028's "Bad" bullet on this point.

  1. Unknown incident: SA404.
  2. The responder never held an assignment on it, open or released: SA403.
  3. The incident is `closed` or `merged`: return `closed`.
  4. A row exists for (incident, responder, status): return `recorded` with the stored `recorded_at` (the retry case). This comes before any check of an open assignment, so a callback retried after a final status released the assignment gets its first answer.
  5. The responder's assignment on it is released (their final status ended their part): return `out_of_order`.
  6. Order, from that responder's own earlier rows. Each failure returns its result:
     - anything after `withdrew_unsafe`: `out_of_order`;
     - `cannot_find` after `arrived`: `out_of_order`;
     - `withdrew_unsafe` after `departed`: `out_of_order`;
     - `departed` without `arrived`: `arrive_first`;
     - `at_facility` without `departed`: `depart_first`.
  7. `at_facility` needs a facility in `op.facilities` of `p_gazetteer_version`, or `other`; otherwise SA422. Any other status with a facility: SA422.
  8. Insert the row. Call `op.append_event_core(…, actor 'responder', idem 'field:'||status||':'||responder, logic NULL)`. Set `event_id` and `recorded_at` from its result.
  9. `cannot_find` → `op.dispatch_escalate(p_incident, 'cannot_find', role, NULL)`. `withdrew_unsafe` → `'scene_unsafe'`. Neither releases the assignment (O17). A transporter's `at_facility` or a VHT's `departed` releases it ("Part A addition", below).

**Rules.** The signature does not determine these. Each action happens once: calls are keyed by (purpose, slot), records by idem key, escalations by key.
- Nothing is planned when `Done`, or when `AcceptedAt` is zero.
- **For each arrival without the idem key `plausibility:<responder>`:** when `Placed`, an `ActVerify` plausibility record (implausible or plausible, `ZoneDistance`, `ElapsedSeconds = ArrivedAt − AcceptedAt`).
- **For each arrival without `variance:<responder>`:** when `UniformIntervals` judges, an `ActVerify` variance record (uniform or varied, `SampleSize`, `CV`).
- **Arrival branch (T5 set):**
  - If a `yes` or a `no` at or after T5 exists, no call is made. An answer to a poll before T5 was about silence, not this arrival, so it neither confirms the arrival nor stops its call. The `no` was escalated by the database (Task 7). The planner also escalates `ReasonArrivalDenied` if the key is missing.
  - Otherwise slot k is due at T5 + (k−1)·`ArrivalRetry` while it is before T1 + `ConfirmationWindow`. Slot 1 is always due, even when T5 is past the window.
  - At T1 + `ConfirmationWindow` with no answer: `ActVerify{KindCaller, ResultUnreached, IdemKey: "caller:unreached"}`.
- **Silent branch** (no arrival and not `Reported`):
  - Poll slot k is due at AcceptedAt + `SilentAfter` + (k−1)·`PollInterval`, while ≤ AcceptedAt + `PollUntil`.
  - Escalate `ReasonSilent` once when a poll slot's due time + `AnswerTimeout` passes with no `yes` recorded between that due time and that deadline, or when a `no` arrives. A `yes` recorded after the deadline, which a late planner sees together with it, does not cancel the escalation. The deadline is counted from the slot's due time, never from `RequestedAt`, so a late or refused request cannot move it: the first is AcceptedAt + `SilentAfter` + `AnswerTimeout`, whether or not any call was placed. This absolute deadline is what pins Review Focus 2.
  - A `yes` stops polling.
- `Reported` without an arrival (cannot-find or withdrawal, already escalated): no polling.
- The wake is the earliest future due time among the next slot, the next silent deadline and the window's end.

**Rules:**
- **`record_verification` and `record_caller_answer`:**
  - Each inserts once per (incident, idem) and writes `op.log_record(..., 'verification.recorded', incident, staff, salt, {kind, result})`.
  - The second call with the same idem returns false or `duplicate`.
  - A closed incident is refused only by `record_caller_answer`, which returns `closed`. Slips, in Part C, verify closed incidents.

- **`request_confirmation_call`** refuses a closed or merged incident (returns false).
- **`claim_confirmation_calls`:**
  - moves `requested` to `claimed` with `FOR UPDATE SKIP LOCKED`;
  - only for incidents not closed or merged, and with no answer that settles the call: any `yes` for a poll; a `yes` or a `no` at or after T5 for an arrival call (the `no` is already escalated);
  - a claimed call is never re-claimed.
- **`return_session_incident`:**
  - On a session's first callback it pins and returns the caller's newest incident that meets all of these:
    - its own sessions' `phone_mac` is in `p_macs`;
    - T4 is set;
    - its state is in (`assigned`, `on_scene`, `transporting`, `at_facility`);
    - no `yes` is recorded at or after T5 (or none at all while T5 is unset);
    - now < T1 + `p_window`.
  - Otherwise it pins NULL.
  - Later callbacks return the pin. Pins older than 1 hour are pruned at pin time, as 0020 does.

## Rulings carried into execution

**Field events get a twin-row guard in `op.append_event_core` instead of a new refusal in the wrapper.**
- Why: the wrapper must not be replaced. A field event whose payload names its function's own unlinked row cannot come from anywhere else.
- Cost if wrong: one function.

**Verification results, Tool 2 reports and slips are ledger-only records, not incident events.**
- Why:
  - they change no state;
  - weekly reconciliation must verify closed incidents, which take no events;
  - there is precedent in the control log (ADR-0026).
- Cost if wrong: one event type and an exact transition from `closed` per record kind.

**The field planner shares the dispatch engine's timer and pass, and runs only after the dispatch planner settles.**
- Why:
  - one wake per incident (ADR-0024);
  - dispatch first;
  - a failure is escalated, as dispatch's are.
- Cost if wrong: a separate loop.

**An unsafe withdrawal keeps the assignment open (O17).**
- Why: the role stays covered without a planner change. An automatic re-alert would send a second lay responder into a scene a peer judged unsafe, uninformed.
- Cost: the withdrawn responder is not alerted again until the incident closes. That is already true of every assignment until M5's close (see below).

**The responder's zone "at dispatch" is their stage's zone in the gazetteer in force at arrival.**
- Why: a stage is fixed at registration (`op.register_responder` inserts only), and the gazetteer is frozen in the window.
- Shortcut, upgrade when M5 lets the console change a stage: snapshot the stage cell on the assignment at acceptance.

**Part A addition: release the assignment on the responder's final field status** (audit SO-9, `docs/explanation/ux-audit-2026-11.md`; this replaces an earlier "not M3" note).

- **Why.** An assignment is otherwise released only by closure, which M5 builds. Until then a responder who accepted once is never alerted again (`BusyResponders`), and the pool shrinks with every call.
- **What.** The SQL function that records a field status (Task 2) also sets `op.assignments.released_at` for that responder's open assignment when the status is final for their role:
  - transporter: `AT_FACILITY`;
  - VHT: `DEPARTED`.
- **Not on `CANNOT_FIND` or `WITHDREW_UNSAFE`.** Both keep the assignment open, as Task 2 step 9 and O17 require: the role stays held, so no second responder is sent into a scene a peer judged unsafe until the Medical Director approves a re-dispatch rule, and the coordinator is rung. Whether a cannot-find should free the responder is part of O19.
- **The release frees the responder, not the role.** The dispatch snapshot's `DispatchAssignments` drops its `released_at IS NULL` filter, so a released role stays in `Assigned`: the planner never re-alerts it and never escalates `red_no_acceptance` for it. Until M5 adds a coordinator release, the final-status release is the only one. The busy checks (`BusyResponders`, the accept guard, surge) keep reading `released_at IS NULL`.
- **Same transaction.** The release happens in the same transaction as the event, so a busy responder becomes eligible again exactly when their part ends.
- **The menu.** 0029 replaces `op.responder_menu_alert` (0020), signature unchanged. `assigned` is true while the session's alert has an assignment, open or released by a final status, on an open incident. A callback retried in the same session after the release therefore takes the same path and gets its first answer (Task 2, step 4). Test: `TestARetriedFinalStatusGetsTheSameScreen` (wiring): `1*5*1` twice in one session gives identical END screens.
- **Open decision O19.** The definition of "final" is a protocol decision. This is the safe default, flagged for the PI; it ties to M4's payment trigger.
- **Test** (in Task 2's tests): `TestAssignmentReleasedOnFinalFieldStatus`.
  - A transporter who reports `AT_FACILITY` is eligible again, and alerted for the next incident.
  - A VHT who reports only `ARRIVED` stays busy.
  - A VHT who reports `WITHDREW_UNSAFE` stays busy, and no second VHT alert is issued.
  - After the transporter's release, the planner issues no transporter alert and no `red_no_acceptance` (`TestReleasedRoleIsNotReAlerted`).
  - The release is in the incident's event log.
  - No coordinator override is needed.
